# SentinelHost — Normalized Result Schema and Adapter Contract

Version: 0.1.0 (design draft)

SentinelHost implements no detection engine of its own. It orchestrates existing
open source engines (maldet, PHP Malware Finder/YARA, AMWScan, Wordfence CLI,
ClamAV when available) and cross-checks their results into one consensus verdict.
The project's two foundations are: (1) the **normalized schema** every engine's
output is converted into, and (2) the **adapter contract** each engine has to
satisfy in order to be plugged in.

---

## 1. Normalized result schema

Every adapter converts its engine's raw output into this schema (JSON). It is the
only language the verdict engine understands.

### 1.1 `Finding` — an individual finding

```json
{
  "schema_version": "1.0",
  "id": "f_9f8a7b6c",
  "engine": "php-malware-finder",
  "engine_version": "0.9.2",
  "rule": "ObfuscatedPhp",
  "rule_ref": "https://github.com/nbs-system/php-malware-finder",
  "file": {
    "path": "/home/user/public_html/wp-content/uploads/2026/07/cache.php",
    "size_bytes": 14382,
    "sha256": "e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855",
    "md5": "d41d8cd98f00b204e9800998ecf8427e",
    "mtime": "2026-07-21T14:03:22-03:00",
    "owner": "user",
    "perms": "0644"
  },
  "category": "obfuscation",
  "severity": "high",
  "confidence": "heuristic",
  "matched_content": "[redacted: dynamic evaluation over a decoded request body]",
  "matched_offset": 1024,
  "scan_id": "s_20260723_0300",
  "detected_at": "2026-07-23T03:04:11-03:00"
}
```

Fields and domains:

| Field | Type | Rules |
|---|---|---|
| `schema_version` | string | Semver of the schema. Adapters declare which version they emit. |
| `id` | string | Generated by the orchestrator (not by the adapter). |
| `engine` | string | Unique slug of the engine (`maldet`, `php-malware-finder`, `amwscan`, `wordfence-cli`, `clamav`, `wp-checksums`). |
| `engine_version` | string | Version of the binary/rules at scan time. |
| `rule` | string | Name of the signature/rule that matched, as the engine reports it. |
| `category` | enum | `known_malware`, `obfuscation`, `backdoor`, `webshell`, `injection`, `spam_seo`, `phishing`, `dropper`, `core_integrity`, `suspicious_location`, `suspicious_perms`, `other`. Each adapter keeps a rule→category mapping table; whatever does not map becomes `other`. |
| `severity` | enum | `critical`, `high`, `medium`, `low` — the severity **as the engine sees it**, normalized by the adapter. |
| `confidence` | enum | `signature` (exact hash/signature), `heuristic` (pattern/behaviour), `anomaly` (out of the ordinary, with no signature). It feeds the vote's weight. |
| `matched_content` | string | The snippet that triggered the rule, truncated to 512 bytes and **sanitized** (never executable). Optional. |
| `file.sha256` | string | Mandatory. It is the deduplication key across engines: the same file flagged by N engines = N votes on the same target. |

> The example above keeps `matched_content` redacted on purpose. This document is
> read on workstations that run an antivirus, and a snippet that looks like a live
> payload gets the file quarantined — which is exactly how this document was lost
> twice (`DECISIONS.md` D-012). The rule the adapters follow is the same one:
> malicious content never needs to travel through the system for the user to
> understand a finding.

### 1.2 `ScanReport` — the result of one engine execution

```json
{
  "schema_version": "1.0",
  "scan_id": "s_20260723_0300",
  "engine": "amwscan",
  "engine_version": "0.15.1",
  "signatures_updated_at": "2026-07-20T00:00:00Z",
  "started_at": "2026-07-23T03:00:05-03:00",
  "finished_at": "2026-07-23T03:04:41-03:00",
  "scope": {
    "root": "/home/user/public_html",
    "mode": "incremental",
    "files_considered": 18234,
    "files_scanned": 412,
    "skipped_reason_counts": { "unchanged": 17801, "too_large": 12, "unreadable": 9 }
  },
  "status": "completed",
  "error": null,
  "resource_usage": { "wall_seconds": 276, "max_rss_mb": 84 },
  "findings": [ /* an array of Finding */ ]
}
```

`status` ∈ `completed`, `partial` (finished with errors on part of the files),
`failed`, `timeout`, `killed` (a resource limit). A `ScanReport` with
`status != completed` **never** counts as "the engine found nothing" in the
consensus — it counts as an abstention.

### 1.3 `Verdict` — the consolidated decision per file

Produced by the verdict engine, never by adapters.

```json
{
  "schema_version": "1.0",
  "verdict_id": "v_3c2d1e",
  "file_sha256": "e3b0c44...",
  "file_path": "/home/user/public_html/wp-content/uploads/2026/07/cache.php",
  "level": "confirmed",
  "score": 0.93,
  "votes": [
    { "engine": "maldet", "weight": 1.0, "finding_id": "f_1a2b" },
    { "engine": "php-malware-finder", "weight": 0.8, "finding_id": "f_9f8a" },
    { "engine": "wp-checksums", "weight": 1.5, "finding_id": "f_5e6f" }
  ],
  "abstentions": ["clamav"],
  "action_taken": "quarantined",
  "action_at": "2026-07-23T03:05:02-03:00",
  "quarantine_ref": "q_20260723_000132",
  "acknowledged_by_user": false
}
```

Verdict levels and the default action (everything configurable):

| `level` | Default criterion | Default action |
|---|---|---|
| `confirmed` | score ≥ 0.9 — e.g. 2+ engines with `confidence=signature`, or a divergent official checksum + 1 engine | Automatic quarantine + alert |
| `likely` | 0.6 ≤ score < 0.9 — e.g. 2 heuristic engines agreeing | An "action recommended" alert, waits for a decision |
| `suspicious` | 0.3 ≤ score < 0.6 — 1 heuristic engine, or an anomaly | Enters the report, with no immediate alert |
| `clean` | score < 0.3 or whitelisted | Nothing |

Fixed rules of the engine (not configurable, for safety):
- A file on the **user's whitelist** is never quarantined, but it stays in the report if engines flag it.
- A file identical (sha256) to the **official WordPress core/plugin checksum** is never quarantined, regardless of votes — engines produce false positives on legitimate minified files.
- Quarantine is always **reversible**: move + record, never delete. A permanent purge happens only manually or after the configured retention (30 days by default).

## 2. Adapter contract

Each engine is integrated by an adapter that implements this interface (Go;
illustrative names):

```go
type Adapter interface {
    // Identity and metadata
    Info() AdapterInfo // slug, name, license, homepage, supported categories

    // Detects whether the engine runs IN THIS environment (binary present, a
    // sufficient PHP/Python version, permissions). Returns
    // Available/Unavailable+reason.
    Probe(ctx context.Context, env Environment) ProbeResult

    // Installs or updates the engine in the user's space (without root), where
    // supported. E.g. downloading AMWScan's phar, cloning the YARA rules.
    Install(ctx context.Context, env Environment) error

    // Updates signatures/rules, if the engine keeps them separate from its
    // installation.
    UpdateSignatures(ctx context.Context) (updatedAt time.Time, err error)

    // Runs the scan over a list of paths (the ORCHESTRATOR decides the list —
    // incremental by mtime/baseline; the adapter does not choose the scope).
    // It has to honour ctx (timeout/cancel) and the resource limits it is given.
    Scan(ctx context.Context, req ScanRequest) (RawOutput, error)

    // Converts the engine's raw output into the normalized schema.
    // Separate from Scan() so old output can be reprocessed when the
    // rule→category mapping improves.
    Parse(raw RawOutput) (ScanReport, error)
}
```

Obligations of every adapter:

1. **It never writes outside SentinelHost's working directory** (except the scan itself, which is read-only). The orchestrator is what moves a file into quarantine.
2. **Execution through a subprocess** with `nice`/`ionice`/ulimits applied by the orchestrator; the adapter declares its relative cost in `Info()` (light/medium/heavy) so the scheduler can interleave.
3. **The raw output is preserved**: `RawOutput` (stdout/stderr/log files) is archived for N days for auditing and for reprocessing through `Parse`.
4. **An explicit mapping** rule→(`category`, `severity`, `confidence`), versioned next to the adapter; an unknown rule → `other`/`medium`/`heuristic`, never discarded.
5. **Isolated failure**: a panic or timeout in one adapter does not take the cycle down — it becomes `ScanReport{status: failed}` and an abstention in the consensus.
6. **Licenses**: GPL engines are invoked as external processes (output through the CLI), with no code linked — the orchestrator can keep its own license (MIT/Apache-2.0).

### 2.1 The MVP's adapters

| Engine | Type | Requirements | Role in the consensus |
|---|---|---|---|
| `wp-checksums` (native) | Integrity through the official WordPress.org API | Network only | The maximum-weight vote (1.5): a tampered core is almost a certainty |
| `php-malware-finder` | YARA rules | the `yara` binary OR an embedded Go YARA library | Strong heuristics for obfuscated PHP (0.8) |
| `amwscan` | Pure-PHP scanner (phar) | PHP CLI ≥ 7.1 | Runs on any hosting; signatures + heuristics (0.8) |
| `maldet` | Signatures + hex | Linux, works partially without root | Mature signatures (1.0) |
| `wordfence-cli` | Free commercial signatures | Python ≥ 3.8, a free license | Strong on WordPress (1.0) — post-MVP |
| `clamav` | General antivirus | Rarely available without root | Opportunistic (0.6) — post-MVP |

The project's first validation target: `wp-checksums` + `amwscan` +
`php-malware-finder` running together on a test directory with known webshell
samples (EICAR-like for PHP) and a clean WordPress, measuring the consensus's hit
rate against each engine on its own.

## 3. A second kind of engine: vulnerabilities (prevention)

Beyond detecting malware that is already installed (reaction), SentinelHost
orchestrates engines that detect **vulnerable components before exploitation**
(prevention): out-of-date plugins/themes/core with a known CVE, vulnerable
Composer/npm dependencies and insecure configuration.

### 3.1 Extending the schema

`Finding` gains the discriminating field `kind`:

| `kind` | Meaning | Possible action |
|---|---|---|
| `malware` | A malicious file (sections 1–2) | Reversible quarantine |
| `vulnerability` | A component with a known flaw | **Never quarantined** — an alert + update guidance |
| `hardening` | Insecure configuration | An alert + guided correction (optionally automatic) |

`kind=vulnerability` findings carry the `component` block in place of
`matched_content`:

```json
{
  "kind": "vulnerability",
  "engine": "wf-vulndb",
  "component": {
    "type": "wordpress-plugin",
    "slug": "contact-form-7",
    "installed_version": "5.7.1",
    "fixed_in": "5.7.2",
    "vuln_ids": ["CVE-2023-XXXXX"],
    "cvss": 8.8,
    "exploited_in_wild": true
  },
  "category": "vulnerable_component",
  "severity": "critical",
  "confidence": "signature"
}
```

Vulnerability verdicts are consolidated per **component** (slug + version), not per
file, and have their own levels: `urgent` (CVSS ≥ 9 or known active exploitation),
`recommended` (a fix is available), `informational` (no fix published yet). Malware
and vulnerability never mix into the same score — they are parallel pipelines that
share the orchestrator, the alerts and the panel.

Synergy between the pipelines: when a `confirmed` malware verdict happens on a site
that had an open `urgent` vulnerability, the report correlates the two ("the likely
way in"), guiding the user to update after the cleanup — otherwise reinfection is a
matter of days.

### 3.2 Vulnerability adapters evaluated

| Engine | License | Coverage | Role |
|---|---|---|---|
| `wf-vulndb` (native) | Wordfence's free public API | WP plugins, themes and core by version | The main one for WP in the MVP: compare installed versions against the feed, with no token |
| `wpscan` | Open source CLI; the DB through an API with a limited free tier and commercial restrictions | Full WP + enumeration | Optional, bring-your-own-token; it cannot be a mandatory dependency |
| `osv-scanner` (Google) | Apache-2.0 | composer.lock, package-lock.json etc. through OSV.dev | Laravel/Composer sites and themes with a JS build |
| `composer audit` / FriendsOfPHP advisories | MIT/free | PHP dependencies | A light fallback when Composer is present |
| `retire.js` | Apache-2.0 | Bundled JS libraries (an old jQuery, etc.) | Complementary, low cost |
| `hardening` (native) | — | 777 permissions, exposed `.env`/`.git`/backups, debug on, directory listing, the wp-admin file editors | Cheap in-house checks, with no dependencies |
| `semgrep` OSS | LGPL (engine) | Insecure patterns in the user's own code | Post-MVP — heavy for cheap hosting |

Detecting the installed version is the orchestrator's responsibility (a parser for
WP plugin/theme headers, `wp-includes/version.php`, lockfiles), so that
data-source adapters (`wf-vulndb`, `osv-scanner`) stay simple.
